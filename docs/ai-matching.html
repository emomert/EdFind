EdFind engineering · AI matching deep-dive

How EdFind's AI matching actually works

A walk through the live code path that takes ten quiz answers, runs them against 196 European master's programs, and returns three ranked matches with a personalised rationale — synchronous, validated end-to-end, and cheap enough to run inside a single Vercel function call.

What this document is

This is a code-level explanation of EdFind's matching pipeline, not a marketing overview. Every code block below is a real excerpt from the current main branch. File paths are shown on each snippet so you can jump to the source.

The full pipeline at a glance:
  1. Quiz client collects 9 typed answers + 1 free-text into a draft kept in localStorage.
  2. Server Action validates the payload with a Zod schema (AnswersSchema).
  3. Persist + match server function inserts the profile, loads the catalog, calls DeepSeek, persists the matches.
  4. DeepSeek V4 Flash receives a system prompt + the profile + the catalog as JSON, returns 3 ranked matches.
  5. Output validator re-parses the JSON, checks the Zod schema, drops any program_id not in the catalog.
  6. Redirect to /results/[matchId], which reads the rationale straight from matches.rationale.

1 The answer shape

Every column the matcher sees comes from lib/quiz/schema.ts. The Answers type is the single source of truth — TypeScript propagates it to the UI, the Server Action, the AI prompt builder, and the database column. A change here ripples everywhere at compile time. 

lib/quiz/schema.ts
export type Answers = {
  destinations: Destination[];
  field_of_study: FieldOfStudy | null;
  budget_per_year: BudgetBracket | null;
  duration_preference: Duration | null;
  english_level: EnglishLevel | null;
  scholarship_need: ScholarshipNeed | null;
  career_goal: CareerGoal | null;
  academic_focus: AcademicFocus | null;
  work_experience: WorkExperience | null;
  // Optional free-text. Lets the student volunteer anything that
  // doesn't fit a multiple-choice box (specific labs, family in a
  // city, motivation). Fed to the matcher verbatim and quoted back
  // in the rationale.
  additional_context: string | null;
};

The 9 structured fields are typed unions whose members are the exact strings the quiz UI emits. They're also what the matcher sees in the prompt — there's no translation layer between "user picked option X" and "the AI received option X".

2 Server-side validation Zod

The quiz client never trusts itself. When the user hits "See my matches" the answers go through AnswersSchema.safeParse(...) on the server before anything else happens. A malformed payload (extra key, invalid enum value, empty destinations) is rejected with a typed error. 

lib/quiz/schema.ts
export const AnswersSchema = z.object({
  destinations: z.array(z.enum(DESTINATIONS)).min(1),
  field_of_study: z.enum(FIELDS_OF_STUDY),
  budget_per_year: z.enum(BUDGET_BRACKETS),
  duration_preference: z.enum(DURATIONS),
  english_level: z.enum(ENGLISH_LEVELS),
  scholarship_need: z.enum(SCHOLARSHIP_NEEDS),
  career_goal: z.enum(CAREER_GOALS),
  academic_focus: z.enum(ACADEMIC_FOCUS),
  work_experience: z.enum(WORK_EXPERIENCES),
  // Optional and bounded — null or empty string when the student
  // skipped it. Defaulted on the server when older clients submit
  // a v2 payload.
  additional_context: z
    .string()
    .max(ADDITIONAL_CONTEXT_MAX_LENGTH)
    .nullable()
    .optional()
    .default(null),
});

Why this matters: the matcher prompt is constructed from the parsed output, not the raw input. If validation passes we know every field is in its allowed enum or null — the AI can never receive (and therefore can never hallucinate around) a junk value.

3 Loading the catalog

Once the profile is persisted we load all the programs the matcher should consider. The query is intentionally wide — the catalog is small enough (~200 rows) that loading everything is faster than running another LLM call to pre-filter. 

lib/server/persist-and-match.ts
const programsRes = await supabase
  .from("programs")
  .select(
    `id, slug, name, degree, field_of_study, language, duration_months,
     tuition_per_year, currency, description,
     qs_subject_rank, qs_subject_area,
     university:universities!inner(name, country, city, qs_world_rank, is_partner)`,
  );

Each row is mapped into the flat ProgramForMatching shape the prompt builder expects. The university join is denormalised here so the AI sees a single flat object per program rather than nested data.

4 Building the prompt

The system prompt is a single long string in lib/ai/index.ts. It does four things, in order: declares the JSON output shape, enforces a rationale style, defines hard filters, and defines soft fits. 

lib/ai/index.ts (excerpt — the contract)
const SYSTEM_PROMPT = `You are EdFind's matching engine. EdFind helps
Turkish students find master's programs in Europe. Given a student's
profile and the full catalog of available programs, return the 3
best-fit programs ranked by overall match.

Output strict JSON in this exact shape, with no markdown, no
commentary, no extra keys:

{
  "matches": [
    { "program_id": "<exact UUID from catalog>",
      "score": 0-100,
      "rationale": "<2-3 sentence personalised paragraph>" },
    ... (3 entries total, ordered highest score first)
  ]
}`;

Hard filters tell the model what it must never include in the top 3. Soft fits tell it what to weigh. The free-text additional_context field is treated as a strong soft signal — strong enough to override a generic destination preference if the student mentioned a specific city. 

lib/ai/index.ts (excerpt — hard filters)
- Hard filters (a program failing any of these should never be in the
  top 3 unless nothing else qualifies):
  · Destination: if the student's destinations does NOT include "ANY",
    restrict to programs whose country is in the destinations list.
  · Language: if english_level is "intermediate", prefer programs whose
    language is "en" with milder requirements; never recommend a
    non-English program if the student's English is weak.
  · Budget: "<10k" rules out anything above ~10,000 EUR/year (convert
    non-EUR roughly: 1 GBP ≈ 1.18 EUR, 1 CHF ≈ 1.05 EUR, ...).
  · Duration: respect duration_preference unless "flexible".

The user message is a JSON-serialised dump of the profile plus a compact view of the catalog. Each program's description is truncated to 240 chars to keep total token count tight.

5 Calling DeepSeek V4 Flash

Every model call goes through a single wrapper in lib/ai/client.ts. It enforces a 25-second timeout, retries once on 5xx or network failure, and short-circuits via the AI_DISABLED env if we need to kill the feature without redeploying. 

lib/ai/client.ts (excerpt — retry loop)
for (let attempt = 1; attempt <= maxAttempts; attempt++) {
  const controller = new AbortController();
  const timeout = setTimeout(() => controller.abort(), DEFAULT_TIMEOUT_MS);

  try {
    const res = await fetch(DEEPSEEK_API_URL, {
      method: "POST",
      headers: {
        Authorization: `Bearer ${apiKey}`,
        "Content-Type": "application/json",
      },
      body: JSON.stringify(body),
      signal: controller.signal,
    });

    if (!res.ok) {
      const isRetryable = res.status >= 500 && res.status < 600;
      if (isRetryable && attempt < maxAttempts) {
        await sleep(400 * attempt);
        continue;
      }
      throw new Error(`DeepSeek API ${res.status}`);
    }
    return await res.json();
  } catch (err) {
    const isAbort = err instanceof DOMException && err.name === "AbortError";
    if (isAbort && attempt < maxAttempts) continue;
    if (isAbort) throw new AiTimeoutError();
    throw err;
  } finally {
    clearTimeout(timeout);
  }
}

The matcher itself sends the request with one important and non-obvious flag: thinking: { type: "disabled" }. 

lib/ai/index.ts (excerpt — the call)
const json = await callDeepSeek({
  model: DEEPSEEK_MODEL, // "deepseek-v4-flash"
  messages: [
    { role: "system", content: SYSTEM_PROMPT },
    { role: "user", content: buildUserMessage(answers, programs) },
  ],
  response_format: { type: "json_object" },
  temperature: 0.55,
  max_tokens: 3000,
  // Disable V4's reasoning step. With thinking enabled the model
  // burns the entire max_tokens budget on reasoning_content and
  // finish_reason becomes "length" before any JSON is emitted.
  // Matching is straightforward enough that direct mode is
  // sufficient and the round-trip is faster + cheaper.
  thinking: { type: "disabled" },
});

Gotcha worth a callout: V4 Flash defaults to its reasoning step. With reasoning on, the model fills reasoning_content until it hits max_tokens and then truncates the visible response — usually before any JSON is emitted. We hit this twice in development before pinning thinking.type to "disabled" on every call.

6 Validating the output

The model's response is treated as untrusted input. We parse it as JSON, run it through a Zod schema, drop any program_id that isn't in the catalog we just sent, and sort by score. 

lib/ai/index.ts (excerpt — output schema)
const MatcherOutputSchema = z.object({
  matches: z
    .array(
      z.object({
        program_id: z.string().min(1),
        score: z.number().min(0).max(100),
        rationale: z.string().min(1).max(900),
      }),
    )
    .min(1)
    .max(5),
});
lib/ai/index.ts (excerpt — defensive parsing)
let parsed: unknown;
try {
  parsed = JSON.parse(content);
} catch {
  throw new Error(`DeepSeek returned non-JSON: ${content.slice(0, 200)}`);
}

const validated = MatcherOutputSchema.safeParse(parsed);
if (!validated.success) {
  throw new Error(`DeepSeek output failed validation`);
}

// Drop hallucinated IDs the model invented.
const validIds = new Set(programs.map((p) => p.id));
const filtered = validated.data.matches.filter((m) =>
  validIds.has(m.program_id),
);

filtered.sort((a, b) => b.score - a.score);
return filtered.slice(0, 3);

Three layers of defence: JSON-parse, schema-validate, ID-filter. If the model ever returns a UUID that isn't in the catalog (it has, on rare occasions, fabricated plausible-looking IDs), we silently drop that suggestion rather than write a dangling foreign key.

7 Persisting + redirecting

The validated suggestions become rows in the matches table. We sort by score, take the highest, and redirect the user to /results/[matchId]. The results page then reads matches.rationale directly — the AI call is one-shot per submission, never re-run on refresh. 

lib/server/persist-and-match.ts
const matchesToInsert = suggestions.map((s) => ({
  profile_id: profileId,
  program_id: s.program_id,
  score: s.score,
  rationale: s.rationale,
  user_id: user.id,
}));

const matchesInsertRes = await supabase
  .from("matches")
  .insert(matchesToInsert)
  .select("id, score");

const sortedMatches = [...matchesInsertRes.data].sort(
  (a, b) => Number(b.score) - Number(a.score),
);
const topMatchId = sortedMatches[0].id;
return { ok: true, matchId: topMatchId };

8 The personalisation layer

The 10th quiz question is a free-text box. Whatever the student types rides through the schema untouched and lands in the prompt as a top-level additional_context field. The system prompt has explicit instructions to quote it back. 

lib/ai/index.ts (excerpt — rationale rules)
- If the student provided "additional_context" (free-text), QUOTE or
  paraphrase at least one specific detail from it in the rationale of
  the matches it actually informs. This is what makes the
  recommendation feel personal rather than generic.
lib/ai/index.ts (excerpt — soft fits)
· additional_context: if the student volunteered free-text (e.g. "I want
  to work with Prof. X's lab", "my partner is moving to Berlin",
  "switching from civil engineering"), use that as a strong soft signal.
  A geographic constraint there can override a generic destination
  preference. A specific lab, professor, or sub-field mentioned should
  bias ranking toward programmes that plausibly host it. Family / partner
  location should weight that city heavily. NEVER fabricate facts about
  the programme to fit the context — if the catalog doesn't confirm it,
  just acknowledge the alignment without inventing details.

The /search page (free-text entry into the matcher) takes a different path: it first calls a second DeepSeek prompt to parse the query into the structured 9 fields, then passes the original verbatim text as additional_context. So both entry points end up calling the same matcher with the same schema — the only difference is how the structured fields were derived. 

lib/ai/parse-query.ts (excerpt — preserving the verbatim query)
// Pass the original query through as additional_context (bounded to

9 Why DeepSeek V4 Flash

Cost

A full matching run is ~6k input tokens (system + profile + 196 programs) and ~1k output tokens. At V4 Flash pricing this is well under a cent per match. Cheap enough to run synchronously inside a single Vercel function.

Latency

Direct-mode (reasoning disabled) returns in ~3-5s on the matcher. The 25s timeout in the client wrapper gives a 5× safety margin. Faster classes of model (Haiku-tier) lose too much rationale quality for the cost saving.

JSON-mode reliability

response_format: { type: "json_object" } plus an explicit shape in the system prompt yields well-formed JSON ~100% of the time in production. We still defensively JSON.parse + Zod-validate.

Forced migration

Legacy deepseek-chat and deepseek-reasoner retire 2026-07-24, so V4 Flash isn't a preference — it's the only supported model. OpenAI sits behind the same wrapper as a future backup.

10 Honest limitations

  • Static FX rates. Budget brackets are quoted in EUR but tuition lives in 7 currencies. The system prompt has approximate GBP/CHF/SEK/NOK/DKK/CZK/PLN-to-EUR rates baked in; they drift over time. See lib/format/currency.ts for the UI-side equivalents and refresh policy.
  • No retrieval. Every program is sent to the model on every call. This is fine at ~200 programs but won't scale past ~1,500 without breaking token budgets. Vector retrieval + re-ranking is the obvious next step.
  • One-shot, no follow-up. The matcher can't ask clarifying questions. If the student's additional_context conflicts with their structured answers (e.g. "I want to be in Berlin" but destinations = Italy), the prompt instructs the model to weight the free-text higher — but we never confirm.
  • No A/B telemetry. We can't yet measure whether students with personalised rationales click into matches more often than those without. Adding this is the next high-leverage move and is currently the biggest blind spot in the system.
